# CSS Animation

Motion is a *style* concern in the browser: transitions, keyframes, and the compositor. Get the property choice wrong and it "works" but drops frames; get `fill-mode` wrong and it snaps back — and neither is a JS bug.

1. **Transition vs animation** — a `transition` animates **between two known values** and only runs when the property changes (`opacity: 0` → `opacity: 1` on a class toggle). `@keyframes` + `animation` is a multi-step timeline that can run on its own, loop, and have intermediate stops. "It didn't animate" usually means you changed a property that has no `transition` declared, or you set the same value on both states (nothing to interpolate).
2. **A transition needs all three parts** — `transition: opacity 200ms ease-out;` is shorthand for **property duration timing-function** (+ optional delay). `transition: 200ms` alone sets only the duration and animates every animatable property; `transition: opacity` alone has a `0s` duration and does nothing. If multiple properties differ, list them (`transition: transform 200ms, opacity 200ms`) or use `transition: all 200ms` knowingly.
3. **You cannot transition to `auto`** — `height: auto → 100px`, `width: auto`, `top: auto` and `display: none` are not interpolatable, so the transition is skipped instantly. Fixes: animate a concrete value, use `grid-template-rows: 0fr → 1fr` for auto-height reveals, `@starting-style` for enter animations, `interpolate-size: allow-keywords` (newer), or measure in JS (see the FLIP rule §12).
4. **`animation-fill-mode` is the "it snaps back" cure** — by default an animation applies its styles **only during playback**, so a `0% → 100%` fade ends by reverting to the element's base style. `animation: fade 300ms forwards;` (`fill-mode: forwards`) keeps the final keyframe; `backwards` applies the `0%` frame during any `delay`; `both` = both. Same trap on a transition: the change must be committed to the class/style or it reverts.
5. **Keyframe syntax** — `@keyframes slide { from { transform: translateX(-100%); } to { transform: translateX(0); } }` (`from`/`to` = `0%`/`100%`; use explicit `50%` stops for intermediate poses). `animation: slide 400ms cubic-bezier(.2,.8,.2,1) 80ms 1 forwards;` shorthand = **name duration timing-function delay iteration-count direction fill-mode play-state** — the *first* time value is the duration, the second is the delay (a common mix-up that makes a "slow" animation instant).
6. **Timing functions** — `ease-out` = fast start, slows to a stop (best for elements **entering**); `ease-in` = slow start (for elements **leaving**); `ease-in-out` = both. `linear` looks mechanical (only use it for continuous loops like spinners/marquees). For real feel use `cubic-bezier(x1,y1,x2,y2)` (control points, x in `0–1`, y can overshoot for a springy pop) — `cubic-bezier(.34,1.56,.64,1)` is a back-out overshoot. `steps(n, end)` is for sprite-sheet/flipbook timing and mechanical ticks, **not** for UI fades.
7. **Animate only `transform` and `opacity`** — these are the properties the compositor can animate without re-running layout or paint. Animating `width`, `height`, `top`, `left`, `margin`, or `box-shadow`/`filter` in a hot path triggers **layout/paint every frame** and janks. Move things with `transform: translate3d()`/`translate()`, scale with `transform: scale()`, and fade with `opacity` instead of `visibility`/`display` where you can.
8. **Transforms don't affect layout** — a translated/scaled element still occupies its original box, so overlapping neighbours won't reflow (usually what you want, but it means a fake "slide" leaves a hole). `transform` is *cumulative* in one declaration (`translate() rotate() scale()`), the **rightmost applies first**, and it always pivots around `transform-origin` (default `50% 50%`) — an off-centre spin is usually a forgotten `transform-origin`.
9. **`will-change` is a scalpel, not a paint roller** — set it *just before* an animation (`el.style.willChange = 'transform'`) and remove it after, or it promotes a compositor layer and burns GPU memory permanently (many promoted layers = worse, not better). Never put `will-change: all` / `* { will-change: transform }` in global CSS. Also don't redeclare the animated property on a child (`transform` on the element, `transform` on its `::after`) — the child's transform resets the parent's influence.
10. **`prefers-reduced-motion` — reduce, don't remove the feature** — gate *movement*, not *feedback*:
    ```css
    @media (prefers-reduced-motion: reduce) {
      *, *::before, *::after { animation-duration: .01ms !important; animation-iteration-count: 1 !important; transition-duration: .01ms !important; }
    }
    ```
    Users who set it (vestibular disorders) still need state changes — a cross-fade or instant state change is fine; a parallax/zoom/bounce is not. JS-driven motion (WAAPI, scroll effects) must check `matchMedia('(prefers-reduced-motion: reduce)').matches` too; the CSS query cannot cover it (see `web-animations-api`, `motion-design`).
11. **Don't block the main thread on the animation's behalf** — a transition/keyframe still runs off the compositor, but a long JS task in the same frame stutters it. Conversely, reading layout (`offsetHeight`, `getBoundingClientRect`) inside a loop forces synchronous reflow — batch reads, then writes ("read everything, then write everything") to avoid layout thrash.
12. **The FLIP technique animates layout changes cheaply** — to animate an element that moved position (list reorder, grid change) without animating `top/left`: **F**irst read `const first = el.getBoundingClientRect()`; make the DOM change; **L**ast read `const last = el.getBoundingClientRect()`; **I**nvert with `el.style.transform = translate(${first.left-last.left}px, ${first.top-last.top}px)` (plus `scale()` for size changes) and clear any transition; **P**lay by adding `transition: transform 300ms` and setting `transform: ''` on the **next frame** (`requestAnimationFrame`). Skipping the rAF makes the browser coalesce both style writes and the element jumps.
13. **View Transitions API** — wrap a DOM change in `document.startViewTransition(() => { /* mutate the DOM here */ })` and the browser snapshots before/after and cross-fades (elements sharing a `view-transition-name` morph between positions). The callback **must perform the DOM change synchronously**; an `await` inside it (a fetch, a state update that hasn't flushed) breaks the snapshot. Feature-detect (`if (!document.startViewTransition) { mutate(); return; }`) — it is Chromium-first, so provide a non-transition fallback (or the FLIP trick). For multi-page, `@view-transition { navigation: auto }` opts in.
14. **CSS-only enters are now possible** — `@starting-style` supplies the "from" styles for an element's first render (works with `display` transitions and popovers/dialogs), which replaces a lot of JS mount-then-toggle-a-class work: `.panel { opacity:1; transition: opacity .2s; @starting-style { opacity:0; } }`.
15. **Verify** — this is browser-observed, not grep-able: drive the page with the browser tool, click the trigger, and assert the *computed* value actually interpolates (`js` op reading `getComputedStyle(el).transform` / `opacity` at ~0ms, ~half, and after the duration), that it ends at the target value (proves `fill-mode`), that `matchMedia('(prefers-reduced-motion: reduce)')` emulation still leaves the final state applied, and screenshot a mid-animation frame (`opacity`/`transform` ≠ end value) — a property that jumps straight to its final value means the transition never ran (see `ui-verification`, `browser-agents`).

## Related skills
- `web-animations-api` — the imperative JS counterpart: `element.animate()`, skipping to a frame, scroll-driven timelines.
- `motion-design` — which easing/duration/stagger to actually use, and the `prefers-reduced-motion` design policy.
- `sprite-animation` — `steps()` + background-position flipbooks, and pixel-art crispness.
- `html5-apis` — `requestAnimationFrame`, `ResizeObserver`, and the platform underneath.
- `static-frontend` / `react-frontend` — where the classes/keyframes live and how a component toggles them.
- `accessibility` — focus states, contrast, and motion that doesn't hijack the user.
- `ui-verification` / `make-it-run` — prove the interpolation in a real browser, not just that it compiles.
