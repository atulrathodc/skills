# Motion Design (UI Animation Principles)

The implementation skills tell you *how* to animate; this one decides *what to animate, how fast, and with what curve*. Motion is feedback and continuity — not decoration. The rule of thumb: if you can delete the animation and the user still understands the interface, the animation must at least not get in their way.

1. **Duration budget — fast, and shorter as things get bigger** — micro-feedback (button press, ripple, toggle): **80–150ms**. Small enter/exit (tooltip, dropdown, toast): **150–250ms**. Panels/modals/page transitions: **250–400ms**. Anything > 500ms feels broken and delays the user. A large element moving a long distance can take longer, but a small one must be snappy — a 400ms tooltip is the same bug as a 40ms modal.
2. **Easing is direction-dependent** — things **entering/appearing** accelerate fast then settle: `ease-out` (`cubic-bezier(0.0, 0.0, 0.2, 1)`). Things **leaving/disappearing**: `ease-in` (`cubic-bezier(0.4, 0.0, 1, 1)`) — they should feel like they're being pulled away. Moves that both start and end on screen: `ease-in-out`. `linear` is only correct for continuous/loop motion (spinners, marquees, progress). The browser default `ease` is a weak, dated curve — define your own set of 2–3 named curves and reuse them.
3. **Anticipation, follow-through, overshoot** — a springy overshoot (`cubic-bezier(0.34, 1.56, 0.64, 1)`, or a real spring via libraries like Motion/`spring()`) reads as playful and physical; a hard stop reads as mechanical. Use overshoot for **confirmation** (a "done" check, an add-to-cart pop), not for high-frequency navigation (every tab switch springing is exhausting). Anticipation = a tiny reverse motion before the action (a wind-up); only use it for one-off, earned moments.
4. **Continuity beats cleverness** — motion's main job is showing *where* something came from and *where* it went. Animate a modal from the button that opened it (or from the edge nearest it), a detail view from the list row it came from, an undo-toast from the element it affects. A generic centre-zoom for everything breaks the spatial model; a shared-element transition preserves it (View Transitions / the FLIP technique — see `css-animation` §12–13).
5. **Stagger & choreography** — when several items animate, don't fire them all at once (a wall of motion) or sequentially (sluggish). Stagger **20–60ms per item** with a cap (first ~8–10 items only, the rest at once — an unbounded `i * 50ms` makes item 40 start two seconds later and feels broken). Animate **enter** in reading order (top→bottom / left→right) and **exit** all together (fast) — leaving slowly is what makes UIs feel laggy.
6. **Choreograph enter vs exit asymmetrically** — enters can be expressive (fade + scale + slide); exits must be **faster and simpler** (usually a fade, maybe a small reverse slide). Don't reverse the full enter animation on the way out — a 400ms entry reversed for a 400ms exit doubles the wait. Overlapping (parent starts, children follow within a frame or two) reads better than a strict sequence.
7. **Micro-interactions are the highest-value motion** — button hover/press (scale `0.97` on `:active`), toggle knob travel, checkbox check draw, input focus ring, drag-and-drop pickup (lift + shadow), copy-to-clipboard confirmation. They must be **interruptible** and never gate input: the state change happens immediately, the animation is a visual echo. A click that waits for the animation to finish (a "loading" button that locks for 300ms) is a bug, not delight.
8. **Loading states: skeleton, don't spin (alone)** — prefer a **skeleton** shaped like the real content (so the layout doesn't jump on load) with a slow shimmer (1–1.5s loop). A spinner is the fallback for content with unknown shape/very short waits. Never show a spinner that never ends without an error/timeout path; and **avoid layout shift** — reserve the exact space the real content will occupy. Animate the skeleton at low contrast; a fast shimmer is more distracting than the wait.
9. **Motion must not thrash layout** — only `transform` and `opacity` in the hot path; animating `width`/`height`/`top`/`margin` reflows every frame and drops frames regardless of how nice the curve is (see `css-animation` §7). Batch DOM reads/writes to avoid layout thrash, and keep animating elements on their own compositor layer only while they animate (`will-change`, removed after).
10. **`prefers-reduced-motion` is a design mode, not an off switch** — the design must still communicate with motion disabled: replace movement with an instant state change or a short cross-fade (never a hard `display:none` pop with no feedback). Never encode meaning *only* in motion (a stagger that reveals reading order, a bounce that signals success) — pair it with a static cue (icon, colour + text, focus ring) so it survives reduced motion **and** screen readers (see `accessibility`).
11. **Direction and distance carry meaning** — the same motion means the same thing every time (forward-navigation slides one way, back the other; an error shakes, success settles). Reserve motion novelties (shake, bounce, wiggle) for genuinely exceptional events — overuse trains users to ignore them. Motion that fights the user's intent (an exit animation they can't interrupt, a modal that fades in while they've already started typing) is worse than no animation.
12. **Performance is part of the design** — budget: layout/paint animation ≈ free at 60fps only for `transform`/`opacity`; anything else must be measured. Test on a **throttled CPU** (4–6× slowdown) and a mid-range phone, not your dev box — a curve that looks great at 120fps can be a slideshow on a cheap device. `animation-fill-mode: forwards` + `will-change` left on globally is a memory leak dressed as polish (§9).
13. **Motion tokens, not magic numbers** — define the set once (`--duration-fast: 120ms; --duration-slow: 320ms; --ease-enter: cubic-bezier(0,0,.2,1); --ease-exit: cubic-bezier(.4,0,1,1)`) and use them everywhere (CSS vars, a JS `motion` config). Ad-hoc per-component durations are why an app "feels inconsistent" — the inconsistency, not any one value, is the tell.
14. **Verify the feel, don't assert a screenshot** — in the browser tool, exercise the real interaction (open the modal, submit the form, reorder the list) and sample the animated values over time to confirm the curve/duration/stagger you intended actually apply (`getComputedStyle(...).transitionDuration`/`animationDuration`, the number of concurrently-running `getAnimations()`), then emulate `prefers-reduced-motion: reduce` and confirm every state is still reachable with motion suppressed (see `ui-verification`, `browser-agents`).

## Related skills
- `css-animation` — implementing transitions, keyframes, FLIP, View Transitions, and `will-change`.
- `web-animations-api` — scripted/seekable/scroll-driven timelines and reduced-motion checks in JS.
- `sprite-animation` — frame-based character/effects motion.
- `accessibility` — reduced motion, focus, contrast, and not encoding meaning only in motion.
- `frontend-design` — layout, hierarchy and visual language that motion serves.
- `react-frontend` / `static-frontend` — where the components and motion tokens live.
- `ui-verification` / `make-it-run` — exercise the interaction and measure the motion at runtime.
