# Lottie Animation

A Lottie file is a JSON description of a vector animation exported from After Effects (Bodymovin) — resolution-independent and tiny compared with a video/GIF. `lottie-web` (aka `bodymovin`, aka `lottie-player` in the web-component form) renders it; almost every failure is a bad path, a double-load, or a renderer/asset mismatch.

1. **Install & load** — `npm install lottie-web` then `import lottie from 'lottie-web'; const anim = lottie.loadAnimation({ container: document.getElementById('lottie'), renderer: 'svg', loop: true, autoplay: true, path: '/animations/hero.json' });`. The `container` element **must already be in the DOM**, and the animation is sized to that container's CSS box — a container with `0×0` (unstyled `div`) renders an invisible animation that "loaded fine".
2. **`path` vs `animationData`** — `path` fetches the JSON at runtime; `animationData` inlines the imported object (`import data from './hero.json'; lottie.loadAnimation({ animationData: data, ... })` with a bundler that supports JSON imports). `path` is relative to the **served root**, so a 404 in the network log is a path bug, not a Lottie bug (see `static-frontend`). Never pass a `file://` path.
3. **Renderers: pick `svg` unless you need otherwise** — `svg` = crisp at any scale, inspectable, stylable, the default. `canvas` = better for very complex scenes with many layers; it rasterises, so it can blur on zoom and isn't styleable via CSS. `html` = for AE text/shape features the other two don't support, and it produces DOM nodes per shape (heavy). Changing the renderer changes what your JSON supports — a file that looks wrong in `svg` may be a `html`-renderer feature.
4. **`loadAnimation` returns an instance — control it, don't re-create it** — `anim.play()`, `pause()`, `stop()`(reset to frame 0 + pause), `goToAndStop(frame, true)`, `goToAndPlay(frame, true)`, `setSpeed(n)` (1 = normal, negative = reverse), `setDirection(-1)`, `setSubframe(true)` (smoother, interpolated frames), `playSegments([[start,end]], true)`, `setProgress(0..1)`, and `addEventListener('complete'|'loopComplete'|'DOMLoaded'|'data_ready', fn)`. Read `anim.totalFrames` for a frame count before seeking; seeking past it silently clamps.
5. **Duplicate loads are the #1 bug** — calling `loadAnimation` twice on the same container stacks two animations into the same node ("the animation got faster/brighter/overlapping" after a remount or an HMR save). Either `lottie.destroy()` / `anim.destroy()` first, or guard with a ref: `if (animRef.current) return; animRef.current = lottie.loadAnimation({...})`. In React, create it in `useEffect` and `anim.destroy()` in the cleanup (StrictMode double-invokes effects in dev — this is exactly what makes the bug appear only in dev).
6. **Respect the container, set the aspect** — Lottie scales to the container's box; if the container's aspect ratio differs from the animation's, use `rendererSettings: { preserveAspectRatio: 'xMidYMid meet' }` (the SVG `preserveAspectRatio` values) to letterbox rather than distort, and give the container an explicit `width`/`height` or `aspect-ratio` in CSS. A hidden (`display:none`) container at mount time can measure `0×0`.
7. **`autoplay` needs a loaded asset — sequence on the event** — `autoplay: true` starts as soon as the animation is ready; if you must seek/interact immediately, register `anim.addEventListener('DOMLoaded', () => { /* container is populated */ })` (or `'data_ready'` for the JSON) instead of assuming it's ready on the next line. `complete` fires **once** for a non-looping animation, `loopComplete` once per loop — wire "hide the loader after play" to the right one.
8. **Dynamic text & theming** — AE text layers become SVG text (`svg` renderer); patch at runtime with `anim.renderer.elements.forEach(el => { if (el.data && el.data.t) el.updateDocumentData({ t: 'New text' }, 0) })` (fragile — prefer a design with a text slot) or theme by setting CSS custom properties if the export used them. The reliable route is editing the JSON's `layers`/`chars` or re-exporting with the text layer split out; the honest answer is "Lottie is not a templating engine".
9. **Big files are a perf problem** — a complex Lottie can be megabytes of JSON and thousands of vector ops per frame. Optimise at export (fewer layers, no effects/expressions, rasterise heavy still layers to an image), consider `renderer: 'canvas'`, and don't run many Lottie instances at once (each is a rAF-driven renderer). For a tiny icon/illustration, a static SVG + CSS is often lighter than the runtime.
10. **Accessibility** — a decorative Lottie should be `aria-hidden="true"` (it's a `div` of `<svg>` with no text); one that conveys information needs a real text alternative (`role="img"` + `aria-label`), and you should pause it (or `goToAndStop` a representative frame) under `prefers-reduced-motion: reduce` — the CSS query does not reach the runtime (see `motion-design`, `accessibility`).
11. **Rive is the interactive alternative** — a `.riv` file + `@rive-app/canvas` (`new rive.Rive({ src: 'x.riv', canvas: el, autoplay: true, stateMachines: 'State Machine 1' })`) supports real state machines and input (`rive.play('bounce')`, boolean/number triggers), so it fits interactive UI (avatars, toggles, game-ish widgets) that Lottie can't express without re-exporting. Trade-off: Rive needs its own editor + runtime; Lottie plays whatever AE produced.
12. **Inspect before you trust** — `https://lottiefiles.com` previews the JSON, and a quick `node -e "const d=require('./x.json'); console.log(d.v, d.w, d.h, d.fr, d.ip, d.op)"` tells you the version/width/height/frame-rate that matter: `op` (out-point) is the frame count to seek within, and a `v` newer than your `lottie-web` version renders wrong (downgrade the export or upgrade the library).
13. **Verify** — in the browser tool, assert the animation *renders and plays*: the container has children after load, `anim.totalFrames > 0`, `anim.currentFrame` **changes** across two samples ~200ms apart while playing, no 404 on the `.json`/`.riv` in the network log, no console errors, and the screenshot is not an empty container. Then `anim.goToAndStop(0, true)` and confirm `currentFrame === 0` to prove control works (see `ui-verification`, `make-it-run`).
