# WebRTC Realtime

WebRTC is peer-to-peer media/data — the transport is direct, but every peer still needs an out-of-band **signaling channel** you write yourself.

1. **Two halves** — (a) the signaling channel (a WebSocket relay you build — see `websocket-realtime`) exchanges SDP + ICE candidates; (b) the `RTCPeerConnection` carries the actual audio/video/data directly between browsers. The media never goes through your server unless you add a TURN relay.
2. **Secure context is mandatory** — `navigator.mediaDevices` is `undefined` on plain `http://` (except `http://localhost`). `getUserMedia` silently missing = you are on `http://<lan-ip>` — use localhost or HTTPS (a self-signed cert + `--ignore-certificate-errors`, or a tunnel).
3. **Permissions** — `getUserMedia({ audio: true, video: true })` rejects with `NotAllowedError` (user denied / no prompt), `NotFoundError` (no device), or `NotReadableError` (device busy — another tab/app holds the camera). Surface the error, don't swallow it.
4. **Show local preview** — `videoEl.srcObject = stream; videoEl.play()` with `videoEl.muted = true` and `playsInline` (autoplay of unmuted media is blocked by the browser). Forgetting `muted` on the local element causes a deafening echo.
5. **Signaling flow (the exact order)** — caller: `createOffer()` → `setLocalDescription(offer)` → send offer → on answer `setRemoteDescription(answer)`. Callee: receive offer → `setRemoteDescription(offer)` → `createAnswer()` → `setLocalDescription(answer)` → send answer. **Both sides must have their local description set before adding/accepting candidates** or the connection never completes.
6. **ICE candidates** — `pc.onicecandidate = e => { if (e.candidate) send({ type: 'candidate', candidate: e.candidate }) }`, and on receipt `await pc.addIceCandidate(new RTCIceCandidate(msg.candidate))`. Candidates can arrive before the remote description (especially over a fast local socket) — **buffer them** and flush after `setRemoteDescription`, or you get `InvalidStateError: The remote description was null`.
7. **Trickle vs non-trickle** — trickle ICE (send candidates as gathered) connects fastest; if you must batch, wait for `icegatheringstate === 'complete'` and send the full SDP. Mixing the two (non-trickle SDP + late candidates) is a classic no-connect.
8. **ICE servers (STUN/TURN)** — `new RTCPeerConnection({ iceServers: [{ urls: 'stun:stun.l.google.com:19302' }] })`. **STUN only reveals your public address; it cannot traverse symmetric NAT.** For real-world connectivity (corporate networks, strict NATs, some mobile carriers) you need a TURN server with credentials (`{ urls: 'turn:host:3478', username, credential }`) — without TURN, same-machine and same-LAN work and everything else hangs at `checking`.
9. **Tracks vs stream** — add media with `stream.getTracks().forEach(t => pc.addTrack(t, stream))` (the `stream` arg is what populates `ontrack`'s `event.streams`). On the far side, `pc.ontrack = e => remoteVideo.srcObject = e.streams[0]`. Adding tracks and *also* passing a confusing `stream` argument is a common source of a remote `<video>` that stays black.
10. **Data channels** — `const dc = pc.createDataChannel('chat', { ordered: true })` (the **caller** creates it; the callee listens via `pc.ondatachannel`). Subscribe to `dc.onopen`/`dc.onmessage`/`dc.onclose` and set `dc.binaryType = 'arraybuffer'` for binary. Sending before `onopen` throws.
11. **Renegotiation** — adding/removing a track mid-call requires a new offer/answer exchange and must be serialized (`makingOffer` / `ignoreOffer` perfect-negotiation flags). Without them, two peers offering at once collide with `InvalidStateError: ... called in state have-local-offer`.
12. **Connection state, not just ICE** — watch `pc.onconnectionstatechange` (`new`→`connecting`→`connected`→`disconnected`/`failed`) and `pc.iceConnectionState`. `connected` on the ICE state with a `failed` connection state means DTLS/SDP mismatch (usually codec or the missing remote description).
13. **Debugging a no-connect** — read `pc.signalingState` / `pc.iceConnectionState` / `pc.connectionState` on both peers, and dump `await pc.getStats()` (`candidate-pair` → check `selected`, `bytesSent`). Candidates that are all `host`/`srflx` with no `relay` means TURN is not configured; `failed` with srflx candidates = symmetric NAT.
14. **Screen share / device switching** — `getDisplayMedia()` for screen; replace a live track with `sender.replaceTrack(newTrack)` (no renegotiation) instead of re-adding.
15. **Cleanup** — `pc.close()`, stop every track (`stream.getTracks().forEach(t => t.stop())`) and clear `srcObject` on unmount/leave, or the camera light stays on and the tab holds the device. Remove listeners from the signaling socket too.
16. **Signaling server shape** — a room-scoped WebSocket relay: join a room, forward `{ offer | answer | candidate }` to the other peer only. Do not broadcast an offer to everyone in the room; the standard failures there are double-answers and interleaved SDP (see `websocket-realtime` for the handshake, auth, and proxy-`Upgrade` pitfalls, and `frontend-backend-integration` for wiring the client).
17. **Verify (two real browsers)** — start the signaling server + frontend (`npm run dev`, background), then open the page **twice** with the browser tool (two contexts/tabs, both `localhost` so it's a secure context), join the same room, and assert both peers log `connectionState === 'connected'` and `iceConnectionState === 'connected'` via a `js` op, with no console errors and a non-blank remote video (`videoWidth > 0`). For a headless run pass fake media: Chromium `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream`. Also curl the signaling HTTP health/endpoint to prove the server is up (see `http-api-testing`, `ui-verification`).
18. **A "signaling server started" is not done** — the proof is a real `RTCPeerConnection` reaching `connected` between two peers.
