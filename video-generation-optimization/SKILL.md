# Video Generation Optimization

Video diffusion burns compute in a few well-understood places: the DiT steps, the quadratic attention over many latent tokens, CFG's doubled forwards, and the VAE decode of hundreds of frames. The vainest work is optimizing the wrong one — if you don't know whether you're step-bound, attention-bound, or decode-bound, you will tune the wrong knob. This skill is the engineering/performance counterpart to `ltx-video` (LTX-Video specifics) and a focused slice of the `optimization-techniques` umbrella; it applies to any DiT video model (LTX, HunyuanVideo, Mochi, Wan, …).

1. **Measure first, freeze the workload** — define the metrics before touching any option: **seconds/clip**, **seconds/frame**, **peak VRAM** (`torch.cuda.max_memory_allocated()/1e9`), **cost/clip**, and **first-frame latency** (time to the first frame vs total). Freeze the workload across every experiment: same prompt, seed, resolution, `num_frames`, steps, guidance, and model + pinned versions. A baseline table is worthless if one number drifts between runs.
2. **Model the attention cost with arithmetic** — DiT attention is quadratic in the token count. Latent tokens ≈ `(num_frames / temporal_compression) × (H/8) × (W/8)` (LTX's temporal compression is 8 for the first block, then fused with spatial; the toy model below still teaches scale). Working example: `49` frames at `768×512` → `(49/8≈7) × 96 × 64 ≈ 43k` tokens; doubling resolution to `1536×1024` at the same frames → `7 × 192 × 128 ≈ 172k` tokens — **4× the tokens**, and since attention is `O(T²)`, compute jumps ~16×. Always run this estimate before choosing a resolution.
3. **Steps and samplers are the biggest lever** — a **distilled** / LCM / Turbo checkpoint converges in single-digit steps; a base checkpoint wants tens. Dropping base 50 steps → 30 can be ~1.7× for free, but judge quality over a **fixed prompt set**, never one clip. Prefer a higher-order or few-step sampler (DPM-Solver++ family, Euler ancestral) that matches the checkpoint's training sampler. Never pay CFG on a distilled model — see §4.
4. **CFG doubles your batch per step** — classifier-free guidance runs two forwards (cond + uncond) per step. Distilled models are trained to run with `guidance_scale≈1` (no CFG), saving ~2×. Where CFG is needed, use APG / CFG-rescale / "distilled guidance" to cut the uncond path, or **batch the cond+uncond passes into one forward** when VRAM allows (do both together so the two parallel branches don't run as two separate serial forwards).
5. **Resolution strategy: generate small, upscale later** — generate at a modest latent size then latent/temporal-upscale (`LTXLatentUpsamplePipeline`, or a Super-Resolution pass) instead of sampling directly at max res. Test whether the two-stage path is *actually* faster than the direct high-res run for your target (it often is, but the second stage's decode can eat the savings — measure it).
6. **Precision: bf16/fp16 baseline, fp8 the transformer only** — bf16 is the safe default. Apply **fp8 to the main DiT transformer** where supported; keep the **VAE and normalization layers in higher precision** — casting the VAE to fp16 frequently yields NaN → **black/garbage frames**. Watch any fp8 path for NaN propagating to black output: run a NaN check on latents before decode, and if you see it, raise the quantized layer's precision.
7. **Verify the attention kernel is actually engaged** — request FlashAttention/SDPA/xformers, then confirm with `torch.backends.cuda.flash_sdp_enabled()` or by reading `torch`/CUDA profiler traces. A kernel that **silently falls back** (warning printed, then SDPA math path) erases the entire win — a "no speedup" report after enabling FlashAttention is usually this. Fuse QKV for the projection to cut memory traffic.
8. **Compile with a cold-start budget** — `torch.compile(transformer, mode="reduce-overhead")` (plus CUDA graphs if supported) gives large steady-state gains but a **long one-time warmup** of Triton compilation. Amortize it over many generations; exclude warmup from reported latency. Dynamo **recompiles whenever shapes vary** — fix and bucket your (frames, W, H) shapes for a batch of generations, or the first different shape re-pays compilation.
9. **Cache the cheap-to-repeat parts** — cache the text-encoder output keyed by (prompt, negative_prompt) — it's identical across seeds/steps. Where cross-attention KV is step-invariant, cache it across steps to skip recomputing the same keys/values each timestep. Memoize the entire result of identical `(prompt, seed, params)` calls so repeat requests return instantly.
10. **Batch and pipeline for serving** — run multiple clips per forward when VRAM allows (batch diag 1 alongside the batch, or use the framework's batch dimension), which amortizes the per-step launch overhead and can raise clips/min even at the same per-clip alloc. For a server, use a **queue + micro-batching** loop and measure **clips/min throughput**, not just per-clip latency — a queue that batches 2–3 coexisting requests often more than doubles throughput at the cost of first-request latency.
11. **Quantization and offload are a VRAM-for-time trade** — int8/fp8 weights (group-wise quant) shrink transformer memory and can *increase* throughput if the workload is memory-bandwidth-bound; CPU/sequential offload cuts peak VRAM sharply at the cost of wall-clock (quantify: "offload saved 8 GB, cost 30% slower"). VAE tiling caps peak decode memory. Only reach for these after precision and kernel wins.
12. **Decode is not free — measure it separately** — the VAE decode of hundreds of frames is often a large slice of total wall-clock and a peak-memory spike. Time the decode in isolation (`t0` before `pipe.vae.decode`, `t1` after) and separate it from denoising in your baseline table. Tile or **chunk the decode** to cap peak memory and keep it off the critical latency path when possible.
13. **Serving and cost-model the cold start** — keep the model warm and reuse it across requests; batch; compute **cost/clip** (GPU-hr × rate / clips). A single-request benchmark is dominated by the cold start that loads GBs of weights — report steady-state per-clip costs and treat cold start as a separate, measured number (see `continuous-batching`, `vllm`, `docker-container` for serving setup).
14. **Regression discipline** — maintain a fixed prompt eval set; keep a baseline table (steps / resolution / VRAM / sec-per-clip) for the unoptimized run; apply **one** optimization at a time and diff before/after; and run a quality check (side-by-side frames, temporal consistency, or a CLIP/similarity score against a reference) so a speed-up that destroys quality is caught instantly. Never ship a video-generation optimization that only reports "faster" with no quality signal.

## Common failures
- **"Enabling fp8/FlashAttention did nothing"** → the fast path never engaged (kernel fell back) or the workload was memory-bandwidth-bound in layers you didn't quantize. Verify kernel selection and profile where the time actually goes.
- **"fp8 made it slower"** → unfused scale application or an fp8 dtype the kernel doesn't support added dequant traffic. Use the kernel-fused fp8 path and re-profile.
- **"Black/garbage frames after quantization"** → the VAE was quantized to fp16/fp8 and hit NaN. Keep the VAE/norms high precision; NaN-check latents before decode.
- **"torch.compile is slower"** → dynamo recompiles on every shape change, or warmup was counted in the latency. Bucket shapes and exclude warmup.
- **"Higher res is way slower than expected"** → you're paying the quadratic token blow-up (§2). Consider generate-small-then-upscale.
- **"Distilled model still slow"** → you kept CFG on (2× per step) or used base-model step counts. Drop CFG and cut steps.

## Verify
- Take one fixed workload (e.g. LTX-Video, 49 frames, 768×512, base steps, seed 0). Record the baseline: `seconds/clip`, `seconds/frame`, `peak VRAM GB`, and a quality signal (CLIP-similarity or per-frame pixel std / inter-frame diff) — with fixed seeds and **warmup excluded**.
- Apply ONE technique (e.g. distilled checkpoint + no CFG, or fp8 transformer, or `torch.compile`), re-measure the identical workload, and report a before/after table (technique, latency, throughput, VRAM, quality) verifying both the speed-up and unchanged/acceptable quality.
- Confirm the attention kernel and fp8 path actually engaged (no silent fallback), and that the resulting video decodes to non-blank, non-identical frames.
