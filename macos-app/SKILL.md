# macOS App

A Mac app is not an iOS app with a bigger window. The build, the sandbox, the signing model, and the
distribution path are all different, and the failure modes ("it's damaged and can't be opened",
`Operation not permitted` on a file that plainly exists) come from those layers rather than your code.

1. **There is no UIKit** — AppKit (`NSApplication`, `NSWindow`, `NSView`, `NSViewController`) is the native framework, and SwiftUI on macOS is a genuinely different implementation, not a reskin: `UIDevice`, `UITabBarController`, and much of the iOS SwiftUI surface do not exist. Check availability before porting iOS code.
2. **The App Sandbox is the #1 macOS-specific surprise** — a sandboxed app cannot read arbitrary paths even though they exist and the process owns them. `Operation not permitted` / `EPERM` on a valid path is almost always the sandbox, not a permissions bug in your code. Mac App Store distribution requires the sandbox; Developer ID distribution does not, but you should still enable it while developing so you find these failures early.
3. **The file picker grants access, a path string does not** — under the sandbox the user selecting a file via `NSOpenPanel` (the powerbox) is what grants access, and the grant is scoped to that selection. Persisting it across launches needs a **security-scoped bookmark** (`url.bookmarkData(options: .withSecurityScope, …)`) and you must call `url.startAccessingSecurityScopedResource()` / `stopAccessingSecurityScopedResource()` around every use — forgetting the `stop` leaks the grant and eventually exhausts it.
4. **Write app data to the container, not next to the app** — use `FileManager.default.urls(for: .applicationSupportDirectory, in: .userDomainMask)`, and create the directory (`.appSupport/myapp`) yourself; it is not created for you. `~/Documents`, `~/Desktop`, and the install directory are all restricted or read-only in practice. `UserDefaults` / `@AppStorage` land in the sandbox container plist, so they appear "empty" if you go looking in the old location.
5. **Entitlements are the capability list** — sandbox, network client/server, file access, camera, microphone, and keychain sharing all require the matching entitlement. A missing network-client entitlement makes every outgoing request fail instantly with no useful error, which looks exactly like a dead server. Entitlement changes require a re-sign and often a clean build.
6. **Signing, hardened runtime, and notarization are three separate gates** — sign with a Developer ID (`codesign --force --options runtime --timestamp --sign "Developer ID Application: …"`), notarize the artifact (`xcrun notarytool submit App.zip --keychain-profile <p> --wait`), then staple the ticket (`xcrun stapler staple App.app`). Skipping the hardened-runtime flag, or leaving any nested dylib/framework unsigned, fails notarization even though the outer app is signed.
7. **"Damaged and can't be opened" is Gatekeeper, not corruption** — an app distributed outside the App Store carries a quarantine attribute and must be signed + notarized to pass. Read the real reason instead of guessing: `spctl -a -vvv -t install App.app` reports the assessment result, and `xcrun notarytool log <submission-id>` names the exact rejected binary or entitlement. For local testing only, `xattr -d com.apple.quarantine App.app` clears the flag — never ship that as the fix.
8. **Pick the distribution path deliberately** — **Mac App Store** (sandbox mandatory, Apple review, Apple handles updates) vs **Developer ID + direct download** (notarization mandatory, no sandbox requirement, you own updates via Sparkle). The choice changes your entitlements and your update code, so decide before you build, not after.
9. **`xcodebuild` needs a macOS destination** — `xcodebuild -scheme <Scheme> -destination 'platform=macOS' -derivedDataPath ./build build` (use `-destination 'platform=macOS,arch=arm64'` to pin an architecture). The built product is `./build/Build/Products/<Config>/<App>.app`; `open` it to actually run it.
10. **Ship a universal binary unless you have a reason not to** — Apple Silicon (`arm64`) and Intel (`x86_64`). Build both and check with `lipo -archs <binary>`; an arm64-only build silently refuses to launch on Intel, and Rosetta covers the reverse only if the user has it installed.
11. **Multi-window is real here** — use SwiftUI scenes (`WindowGroup`, `Window`, `Settings`, `MenuBarExtra`) or `NSWindowController`; macOS has no single-window assumption. `WindowGroup` spawns a new window per `openWindow`, which surprises people porting from iOS where a "window" was the whole app.
12. **The app does not quit when the last window closes** — `applicationShouldTerminateAfterLastWindowClosed` defaults to `false`. Decide explicitly whether you are a document app (stay alive) or a utility (quit), and note a menu-bar-only app usually wants `LSUIElement = true` in `Info.plist` to drop the Dock icon.
13. **Menus and keyboard are the primary UI on Mac** — a Mac app is expected to have a real menu bar with working shortcuts. In SwiftUI add them with `.commands { CommandMenu("…") { Button(…) .keyboardShortcut(…) } }`; in AppKit via `NSMenu`. The responder chain (`NSResponder`) routes actions, so a menu item wired to a selector does nothing unless something in the chain implements it.
14. **Launch-at-login uses `SMAppService`** — `try SMAppService.mainApp.register()` (and `.unregister()`), which requires macOS 13+. The older `SMLoginItemSetEnabled` + helper-bundle approach is deprecated; do not start a new implementation on it.
15. **TCC permissions are granted to a *signed identity*, so unsigned rebuilds lose them** — camera, microphone, screen recording, Accessibility, and Location require the user to grant access in System Settings, and the grant is keyed to the code signature. Ad-hoc/unsigned builds change identity on every rebuild, so the prompt reappears forever ("it keeps asking for permission"). Sign with a stable identity while developing. Screen Recording and Accessibility additionally cannot be granted programmatically and may need an app restart to take effect.
16. **Screen Recording is not a normal permission** — `CGWindowListCreateImage`/`SCStream` return a desktop-wallpaper-only image (no error) until Screen Recording is granted, which is the classic "my capture is blank" report on macOS.
17. **Updates differ by channel** — Mac App Store apps update through the store; direct-distribution apps need **Sparkle** (`SPUStandardUpdaterController`, an appcast XML, and an EdDSA signature per release). An app that never updates leaves users on a build you cannot fix.
18. **Verify by launching the real `.app`** — a SwiftUI preview and a successful build are not a running app. `open ./build/.../App.app`, exercise the feature, and read the logs (`log stream --predicate 'process == "<AppName>"'` or Console.app) because a sandbox or entitlement failure is logged, not shown. Capture a screenshot with `screencapture -x /tmp/shot.png`. If it launches from Xcode but not from Finder, you have a signing/quarantine/path problem, not a code problem.
19. **Re-sign and re-notarize after any binary change** — editing a framework, resource, or nested helper invalidates the signature; a notarized app that you then modify fails Gatekeeper. The last step of every release is always staple + `spctl` verify on the exact artifact you upload.

## Related skills

- `ios-app` — the iOS build/run/signing counterpart; the two share Xcode and Swift but not their app models.
- `swiftui` — the UI framework both platforms use, and where they diverge.
